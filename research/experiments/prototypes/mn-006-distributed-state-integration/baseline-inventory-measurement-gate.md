## Canonical inventory unit and causal interpretation

The inventory unit is an **underlying paired canonical case**, not a single prompt:

```text
pair_id
├── contiguous_control prompt
└── interleaved prompt
```

The two members must share entity histories, initial state, query entities, rule, final-state map, derived fact, canonical answer, answer class, and profile-specific entity/event count. Only global scheduling/order and schedule-derived metrics may differ.

Counts are always reported in both units:

| Profile | Underlying paired cases | Serialized prompts | Answer classes |
| --- | ---: | ---: | --- |
| Level 1 | 32 | 64 | 16 `VALID`, 16 `INVALID` pairs |
| Level 2 | 32 | 64 | 16 `VALID`, 16 `INVALID` pairs |
| Total | 64 | 128 | 32 `VALID`, 32 `INVALID` pairs |

The only primary causal comparison is **within profile**, contiguous versus its matched interleaved form. Level 1 versus Level 2 is descriptive distributed-state-pressure escalation: it jointly changes entity count, total/non-query events, same-entity gap, and relevant span. It is not an isolated locality effect.

## Size and mechanical selection rule

The inventory contains exactly 32 ordinal pairs per profile. This is an even count, yielding exact answer balance through the frozen `VALID, INVALID, ...` ordinal sequence. It is deliberately bounded: 64 pairs retain full per-case traceability and require 128 independent baseline requests, while supplying 16 pairs per answer class in each profile.

Before any model output, only frozen structural checks were used to compare conventional candidate counts. Twelve and 24 pairs failed required Level 2 full permutation-slot coverage under the one predetermined namespace and sequential ordinal rule; 32 passes. Forty-eight also passes but adds requests without a new v1 coverage requirement. The selected size is therefore 32, not a model-performance choice.

For each profile, the generator receives:

```text
root_seed = "mn006-v1-baseline-inventory"
ordinals  = 0, 1, ..., 31
```

The profile identifier is already part of the frozen sub-seed derivation, so the same root namespace produces distinct profile-specific canonical cases. No seed sweep, manual inspection, case deletion, case replacement, difficulty judgment, or model-output filter is permitted. A construction or validation failure is an implementation defect and blocks inventory acceptance; it is not permission to substitute another seed or ordinal.

## Mandatory inventory inclusion and structural coverage

Every pair is included if and only if it is generated by the frozen rule above and all of the following machine-verifiable checks pass:

1. deterministic generation and every single-case semantic/oracle/schedule/public-boundary validator pass;
2. contiguous/interleaved pair equivalence passes;
3. canonical public, evaluator, and authority serialization and fingerprints succeed;
4. public/evaluator/authority visibility boundaries are preserved;
5. each profile has all 32 ordinals and both schedule members for every pair;
6. each profile has exact `16 VALID / 16 INVALID` pair balance;
7. answer-proxy audit passes, including tuple rotation and identical label distribution across schedules; and
8. positional audit with `require_full_slot_coverage=True` passes separately for each profile and answer class.

The retained audit output must record answer × query identity, answer × query permutation slot, answer × final-state tuple, answer × schedule kind, and query position patterns. This coverage prevents accidental locking of query entities to a small set of regular round-robin positions. It does not claim coverage of arbitrary/irregular interleaving: MN-006 v1 remains a regular repeated-permutation round-robin workload.

## Canonical artifact layout, bytes, and manifest

The canonical workload authority is materialized independently of a model run under:

```text
definition/baseline-inventory-v1/
  manifest.json
  public/<profile>/<case_id>.txt
  evaluator/<profile>.json
  authority/<profile>.json
```

`public/` contains only model-visible prompt text. `evaluator/` contains the minimal evaluator records. `authority/` contains provenance and oracle truth. No model response, score, timing, or run metadata belongs in this tree.

Every authoritative JSON object uses sorted-key canonical JSON encoded as UTF-8 with LF and exactly one final newline. Every public prompt uses canonical UTF-8/LF text with exactly one final newline. The materializer must:

```text
canonical object/text
    ↓
canonical bytes and SHA-256
    ↓
binary write (wb)
    ↓
binary read (rb)
    ↓
byte equality and identical SHA-256
```

Text-mode writing is not allowed for fingerprint-authoritative artifacts. The materializer must reject a readback containing CRLF in canonical public text or canonical JSON. This is an MN-006-specific protection against the historical Windows raw-byte authority failure; it does not revise older frozen authorities.

`manifest.json` records inventory/schema/workload/generator/validator versions; root seed rule; profile counts; ordered pair/case IDs; every materialized artifact's relative path, kind, case/profile association, byte count, and SHA-256; coverage/audit results; and an aggregate inventory fingerprint. The aggregate is SHA-256 of canonical JSON containing the inventory identity fields and the explicitly path-sorted artifact entries. It never depends on filesystem traversal order. The manifest's aggregate excludes its own physical-file hash to avoid self-reference.

## Request order, independence, and failures

All 128 prompts are fresh independent requests: no conversational context, cross-request memory, prompt cache, or response-derived state is permitted. Profile order is Level 1 then Level 2. Within each profile, ordinals are ascending. For even ordinals the request order is contiguous then interleaved; for odd ordinals it is interleaved then contiguous. This counterbalances schedule order without changing facts, answer class, or request count.

There are no automatic request retries. A malformed output is a valid measured model outcome and scores zero; it is never retried. Timeout, HTTP/server error, unexpected process exit, OOM, health failure, prompt-token inconsistency, artifact-integrity failure, or interruption is an infrastructure failure that invalidates the whole attempt. The failed request and all prior raw records are retained.

The first attempted run is `attempt-0001`. A later exact whole-inventory re-execution is allowed only after a retained infrastructure incident record identifies the failure class; it receives a new attempt ID, preserves the invalid attempt unchanged, uses the same inventory/runtime contract, and may not change seeds, cases, prompts, scoring, or parameters.

## Response retention and evaluation

For every request, retain immutable raw evidence containing at least:

- attempt/run ID, request ordinal, profile, pair ID, case ID, schedule kind, and inventory aggregate fingerprint;
- exact public prompt SHA-256 and prompt byte count;
- model filename/SHA-256 and runtime/server identity;
- request payload and raw response payload/text;
- parsed label or malformed status;
- canonical answer, exact correctness, failure class, timing, and server/API token metadata when available; and
- infrastructure status/error details.

The strict MN-006 parser is the evaluator: outer ASCII trim followed by exactly one case-sensitive `VALID` or `INVALID`. A malformed response and a parseable incorrect label both score zero but remain distinct diagnostic classes. The evaluator must not call an LLM judge.

For each profile, report:

- contiguous exact accuracy;
- interleaved exact accuracy;
- paired delta `interleaved_accuracy - contiguous_accuracy`;
- malformed-output count by schedule;
- infrastructure-status count; and
- the four matched transitions `C✓→I✓`, `C✓→I✗`, `C✗→I✓`, and `C✗→I✗`.

The principal transition is `C✓→I✗`: the same underlying facts were solved when grouped but failed when distributed. The primary descriptive paired quantities are `b = C✓→I✗`, `c = C✗→I✓`, and `(b - c) / 32`. If inferential reporting is used, it is the predeclared one-sided exact McNemar/binomial test over discordant pairs, `P[X ≥ b]` for `X ~ Binomial(b+c, 0.5)`, only when `b > c`; pairing is never discarded.

## Predeclared interpretation and diagnostic policy

An attempt is **invalid/unusable** if any inventory/hash/validator failure or infrastructure failure occurs. Such an attempt supplies no baseline interpretation.

For a valid attempt, a profile has a **candidate locality-failure signal** only if all of the following hold before looking at results:

1. contiguous exact accuracy is at least `24/32` (75%); this requires materially present matched-case capability rather than a shared floor;
2. `b > c`; and
3. the one-sided exact paired test has `p <= 0.05`.

The 75% capability floor is deliberately above the MN-002 State qualification threshold of 70%, while remaining a finite count (`24/32`) stated before the first output. The paired exact test, rather than an unpaired comparison, supplies the directional degradation criterion. This status is only a workload signal that may justify a later candidate-specific hypothesis gate; it does not select or support an intervention.

If a valid profile does not meet that signal, its outcome is retained as **no usable locality-failure signal under this v1 baseline**. This includes ceiling, shared-floor, small/inconsistent paired degradation, or insufficient contiguous capability patterns; no profile, case, seed, metric, or threshold may then be changed in response.

The perfect-state diagnostic is not run automatically and is not an individual-case rescue. It may be proposed only if a valid profile meets the candidate locality-failure signal, has no infrastructure failure, has at most two malformed outputs among its 64 prompts, and the remaining question is whether state integration rather than the fixed equality rule caused the degradation. A separate static prompt/control contract is required before it can execute. It must preserve the same answer grammar and depth-1 rule.

Candidate interventions remain prohibited until a valid baseline yields at least one candidate locality-failure signal and a later candidate-specific mechanism, matched control, resource account, and anti-oracle contract are frozen.
